# Benchmark snapshot

Dataset: three synthetic, typed, one-page PDFs generated by `scripts/make_sample.py`. The third page is rotated 1.4° and lightly blurred. Ground truth is in the adjacent JSON files. These rows are a software check, not a handwriting benchmark.

| Pipeline | Field exact match by document | Median document latency | Availability |
| --- | --- | ---: | --- |
| OpenCV/custom OMR/Tesseract | 1.00, 1.00, 0.40 | 417 ms | Ran |
| OpenCV/custom OMR/PaddleOCR | 1.00, 1.00, 1.00 | 543 ms | Ran |
| Gemini Vision | 1.00, 1.00, 1.00 | 4,889 ms | Ran with `gemini-3.8-flash` |
| Hybrid | 1.00, 1.00, 1.00 | 538 ms | Ran; no fallbacks triggered |

PaddleOCR loads models on its first run; subsequent runs were about 543 ms each. Gemini used 4,012 total input/output tokens across the three pages. The hybrid route used zero tokens because PaddleOCR marked every field confident; this does not test fallback accuracy or cost. These figures depend on this machine and API response time. Process peak RAM in `benchmark.json` is a high-water mark shared across sequential runs, so it is not suitable for per-route RAM comparison.

On `intake-3.pdf`, Tesseract missed `full_name`, misread the date as `05 Nov 20260 8`, and misread the reference as `REF-3020000`. PaddleOCR and Gemini extracted all five labeled values. Both local routes detected the two selected marks. No tested page contains real handwriting, circles, crosses, erasures, or multiple marks. The current data does not support a production recommendation or a conclusion about Gemini fallback benefit.

For the next benchmark, use the actual target templates and manually labeled completed forms. Preserve scan-quality strata and run each route in an isolated worker to measure peak RAM. Set current token prices before estimating cost and include ambiguous pages to measure fallback correction rate.
